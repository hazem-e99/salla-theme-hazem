# Editor integration report

## Status: schema fixed and validated locally. Live "Add Section" verification is NOT yet done.

This report separates two different things that earlier work in this repository blurred
together: (1) whether `twilight.json` is *structurally* correct, which can be verified by code,
and (2) whether Salla's live Theme Editor actually *registers and renders* every component in the
real "Add Section" library, which can only be verified by a human in an authenticated browser
session (Cloudflare Turnstile blocks automated login — see `LIVE_QA_REPORT.md`). Only (1) is
claimed complete here.

## Root-cause findings

Two concrete, reproducible schema defects were found in the 52 Premium components generated by
`scripts/sync-premium-components.mjs`, compared against the 6 original/legacy components that are
already known to work in the live editor:

1. **Non-UUID component keys.** All 52 Premium components used slug-style keys such as
   `premium-system-hero-001` or `premium-structured-014`, while every legacy component (and every
   component Salla's own theme documentation examples use) has a UUID v4 key such as
   `186b3f4f-25cf-4d3c-abca-cef7eed6f0ab`. Salla's editor is known to be strict about this format
   for registering custom sections in "Add Section" — a non-UUID key is the leading hypothesis for
   components existing in `twilight.json` but not appearing live.
2. **Required dynamic fields with impossible empty defaults.** Three components
   (`home.premium-hero`, `home.product-showcase`, `home.collection-showcase`) declared a
   `required: true` products/categories selector with `selected: []` and `value: []` — i.e. a
   field the editor is told must have a value, shipped with no valid value. This is a documented
   footgun: Salla's editor can silently refuse to register the component, or fail to open its
   settings panel, when a required field has no way to be satisfied at schema-load time.

Everything else was checked and found structurally sound: JSON validity, no duplicate component
keys/paths, no duplicate field IDs within a component, every `path` correctly maps to an existing
Twig file under `src/views/components/...`, complete bilingual (`ar`/`en`) titles, valid
`sicon-*` icons, well-formed `multilanguage` values, correctly dot-namespaced collection
subfields, and no dropdown-list field missing both a dynamic `source` and static `options`.

## What was fixed

- `scripts/sync-premium-components.mjs` now mints a UUID v4 per component **path** (paths are
  stable identifiers) via a persisted map at `scripts/premium-component-keys.json`, which is
  committed to source control. Re-running the generator reuses the same key for the same path —
  it never regenerates a UUID for an already-shipped component, so merchants who have already
  added a section will not have it silently orphaned by a key change.
- The three offending fields (`home.premium-hero` → `products`, `home.product-showcase` →
  `products`, `home.collection-showcase` → `categories`) are now `required: false`.
  `src/views/components/home/premium-hero.twig` and
  `src/views/components/home/product-showcase.twig` were updated so the "product spotlight" /
  "product showcase" sections fall back to `source="latest"` on Salla's native
  `salla-products-slider` / `salla-products-list` web components when the merchant hasn't picked
  products yet, instead of silently rendering an empty shell. `home.collection-showcase` has no
  equivalent native "all categories" web component in this theme (its legacy sibling,
  "Quick Links" / `home.main-links`, has the same constraint), so it stays optional but honestly
  renders nothing until the merchant picks categories — no fake/invented data source was added.
- Every Premium component now also carries an `image` (Add Section preview thumbnail), matching
  the property every legacy component has and closing a parity gap (cosmetic, not a rejection
  cause, but worth fixing).
- `scripts/validate-theme-components.mjs` (new) codifies all of the checks above — including two
  intentional, scoped exceptions for the pre-existing legacy "Animated products with a background"
  and "Brands" components, which have the same required-empty-array pattern but predate this
  project and are out of scope to touch without separately re-verifying them. Run it with
  `pnpm validate:theme-components`; it is also wired in as the first step of `pnpm production` /
  `pnpm development`, so a broken schema now fails the build loudly instead of failing silently in
  the editor.

Current result: `pnpm validate:theme-components` → `OK: 58 components validated, 0 errors, 0
warning(s).` `pnpm production` completes with zero errors (only pre-existing Sass `@import`
deprecation notices and webpack's standard >244 KiB asset-size advisory, both unrelated to this
change).

## What is still unverified — requires the user's own browser session

Live "Add Section" registration cannot be confirmed by this automated session. Cloudflare
Turnstile blocks scripted login, and a preview watcher process was already running against a live
draft (`draft-462507283` at the time of writing) with a browser connected to it — that session
belongs to the user, not to this tool run.

### To verify (exact steps)

1. In a terminal, run (or reuse the currently running preview if you still have it open):
   ```
   salla theme preview --store hazem-test --with-editor --browser chrome
   ```
2. Complete Salla login and the Cloudflare challenge yourself in the opened Chrome window.
3. Once the editor loads, open **Add Section** on the homepage.
4. First, confirm the **minimal test component** below appears, since it is deliberately the
   simplest possible Premium component and isolates the UUID-key fix from every other variable. If
   it does not appear, the problem is not schema-level (see the "if it still doesn't appear"
   checklist below).
5. Then work through the full checklist and fill in each column for every component.

### Minimal test component

A dedicated verification component has **not** been added to `twilight.json` in this pass,
because the fix already applies uniformly to all 52 real components — adding a throwaway 59th
component would just be one more thing to clean up later without adding evidence beyond what
component #7 below (`01 · Hero — Premium`) already gives you. If you want an even smaller,
single-field isolation case before checking all 58, tell me and I will add one; otherwise start
directly with `01 · Hero — Premium`, since it now has a UUID key, a thumbnail, and no
required-empty-array field — the same shape as every other fix in this pass.

### If a component still doesn't appear after this fix

- Confirm the previewed draft is actually reading the pushed `feat/premium-theme-system` branch
  and not a stale draft ID from before these changes (`LIVE_PREVIEW_GUIDE.md` explains draft IDs
  are ephemeral — discard old tabs).
- Confirm `salla theme list` doesn't have you pointed at the wrong one of the two `hazem-dev`
  theme records (IDs `352916197` / `473436942`).
- Hard-refresh the editor tab; Salla may cache the previous schema.
- If it's still missing, that points to a Salla platform-side caching/sync issue rather than a
  schema defect, and is worth reporting to Salla support with the component's exact key and path.
